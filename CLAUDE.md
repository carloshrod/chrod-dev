# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A bilingual (EN/ES) portfolio website for a full stack web developer, built with **Astro 5.x** as a static site generator. Content for projects and reviews is managed via **Sanity CMS**, and the site uses **React** for interactive components, **Tailwind CSS** for styling, and deploys to **Netlify**.

## Commands

All commands run from the project root:

| Command           | Action                                                                                  |
| ----------------- | --------------------------------------------------------------------------------------- |
| `npm run dev`     | Start dev server at `localhost:4321` (pre-clears `.vite` cache to prevent stale builds) |
| `npm run build`   | Build production site to `./dist/`                                                      |
| `npm run preview` | Preview build locally before deployment                                                 |
| `npm run astro`   | Raw Astro CLI (e.g., `npm run astro add`)                                               |

**Notes:**

- Dev server requires environment variables (see setup below)
- Build pre-clears `.vite/` and `node_modules/.vite` to prevent Vite cache issues

## Environment Setup

Copy `.env.example` to `.env.local` and populate with:

- **Resend** (contact form + service quote form): `RESEND_API_KEY`, `RESEND_FROM_EMAIL` (verified sender), `RESEND_TO_EMAIL` (inbox that receives submissions) — server-only, used by `src/pages/api/send-contact-email.ts`
- **Sanity CMS**: `PUBLIC_SANITY_PROJECT_ID`, `PUBLIC_SANITY_DATASET` (defaults to "production")
- **WhatsApp onboarding** (CHRod Connect Tech Provider app): `PUBLIC_WHATSAPP_APP_ID`, `PUBLIC_WHATSAPP_CONFIG_ID` (client-side, from Meta's Embedded Signup config), `WHATSAPP_APP_SECRET` (server-only, Meta app secret — also used as an app access token for `debug_token`; see below), `WHATSAPP_SYSTEM_USER_TOKEN` (server-only, optional — reads `/phone_numbers` on the WABA `debug_token` found; see below), `WHATSAPP_LINK_SECRET` (server-only, signs the per-client onboarding link — see below), `ADMIN_ACCESS_TOKEN` (gates `/es/admin-links`), `PUBLIC_SITE_URL`
- **Review Form**: `SANITY_WRITE_TOKEN` (Editor role from Sanity's API tokens), `REVIEW_ACCESS_TOKEN` (random string to protect `/review` endpoint)
- **Analytics**: `PUBLIC_UMAMI_WEBSITE_ID` (Umami Cloud website id). Set in `netlify.toml` under `[context.production.environment]`, so production is the only context that has it. Leave it unset locally: unset disables analytics rather than failing, and that is what keeps development clicks and deploy previews out of the real numbers.

## Architecture

### Page Structure

- **`src/pages/`**: Route files, nested per locale under `src/pages/en/` and `src/pages/es/`. **URL segments are translated**, so the two locale trees do not mirror each other by name (see Internationalization below).
  - `en/index.astro` / `es/index.astro`: homepage
  - `en/services/…` / `es/servicios/…`: services overview + `[slug].astro` detail pages
  - `en/projects/…` / `es/proyectos/…`: projects listing + `[slug].astro` case-study pages
  - `en/about.astro` / `es/acerca-de.astro`: about page
  - `en/contact.astro` / `es/contacto.astro`: contact page (booking calendar, form, direct channels). Markup lives in `src/components/contact/ContactPage.astro`; see Key Implementation Details 9
  - `en/blog/…` / `es/blog/…`: blog listing + `[slug].astro` articles, from Sanity. Markup in `src/components/blog/`; see Key Implementation Details 10
  - `en/review.astro` / `es/resena.astro`: client review submission form (SSR, token-gated)
  - `en/privacy-policy.astro` / `es/politica-de-privacidad.astro`, `en/terms.astro` / `es/terminos-y-condiciones.astro`: legal pages
  - `404.astro`: **must stay `prerender = false`.** A prerendered 404 gets baked into a single static HTML string that the Netlify adapter returns for every unmatched path, which would serve the Spanish page to someone who mistyped an `/en` URL. Rendering per request lets it read the locale off `Astro.url.pathname`. Markup lives in `src/components/NotFoundPage.astro`.
- **Layout**: `MainLayout.astro` wraps every page with SEO meta tags, fonts, and WhatsApp button. Pass `noindex` to drop the canonical/hreflang set and mark the page `noindex, follow` (used by the 404).

### Component Organization

- **`src/components/layout/`**: Structural (Navbar, Footer, Container)
- **`src/components/sections/`**: Page sections (HeroSection, AboutSection, ProjectsSection, ReviewsSection, etc.)
- **`src/components/ui/`**: Reusable UI pieces (ProjectCardLink, ReviewsCarousel, ContactDrawer, etc.)
- **`src/components/projects/`**: Projects listing (`overview/`) and case-study detail (`detail/`) page sections, mirroring `src/components/services/` structure
- **`src/components/contact/`**: Contact page sections (`ContactPage`, `ContactScheduler`, `ContactChannels`)

### Content Management

**Sanity Integration** (`src/lib/sanity.ts`):

- `getProjects(lang)`: Fetches projects with language-aware GROQ queries; falls back to EN if ES field missing
- `getReviews(lang)`: Fetches published reviews, also language-aware
- Queries include inline translations via GROQ's `select()` for title, description, role, etc.
- Images (screenshots, company logos) resolved via Sanity asset URLs

### Internationalization

**Simple i18n pattern** in `src/i18n/`:

- `ui.ts`: Key-value translation object keyed by locale ("en", "es")
- `utils.ts`: `useTranslations(lang)` hook returns a `t(key)` function; falls back to EN if key missing in target locale
- Components receive `lang` prop and call `t()` to retrieve strings
- No build-time extraction; keys hardcoded in component calls

**Localized URLs** (`src/i18n/routes.ts`) — the single source of truth for route segments:

- `routeBases` maps a stable `RouteKey` (`services`, `projects`, `about`, …) to its per-locale path. Terms that read the same in both languages (landing pages, ecommerce, API, backend) stay untranslated on purpose.
- **Never hardcode a route.** Build hrefs with `getRouteUrl(lang, key, slug?)`, not `getRelativeLocaleUrl(lang, "/services")`.
- `getAlternatePaths(key, slugs?)` returns both locales' paths. Every page passes the result to `MainLayout` (`alternates` → hreflang tags) **and** to `Navbar` (language switcher) — the switcher cannot derive the counterpart URL from the current path, since the segments differ per language.
- `isRouteActive(stripLocale(pathname), lang, key)` drives nav highlighting.
- Changing a segment requires three coordinated edits: the value in `routes.ts`, the folder/file name under `src/pages/<locale>/`, and a 301 in `netlify.toml` for the URL being retired. That file holds the `netlify.app` → `chrod.dev` domain redirect plus ~57 route redirects, with detail pages listed before any splat because a splat would otherwise swallow them. Project slugs are the trap: a `/es/projects/*` splat used to translate the segment while keeping the slug, so once every project had a Spanish slug it answered each old URL with a 301 to a page that no longer existed, and Google followed those redirects and indexed the dead targets too. `assertProjectRedirects` (`src/lib/redirects.ts`, called from `src/pages/es/proyectos/[slug].astro`) now fails the build when a Spanish slug in Sanity retires a URL that has no rule.
- `routes.ts` is deliberately free of `astro:i18n` (it hand-rolls `withLocale`) so client-side React components can import it.

**Slugs are localized too:**

- Services: `Service.id` is a stable identifier (what Sanity stores in a project's `services` array, and what the overview anchors use) — it never appears in a URL. `Service.slug` is a `LocalizedText` holding the URL segment per language. Note `id: "business-websites"` maps to the EN slug `professional-websites`; the id is deliberately frozen so existing Sanity content keeps matching.
- Projects: Sanity has `slug` (EN, required) and `slugEs` (optional). `getProjects(lang)` returns `slug` for the requested language plus `slugs: { en, es }` for hreflang. ES falls back to the EN slug when `slugEs` is empty.

### Styling

- **Tailwind CSS**: via `@tailwindcss/vite` plugin (Vite-first integration)
- **Global CSS**: `src/styles/global.css` (imported in MainLayout)
- Dark theme: site uses `bg-[#06060c]` base, `text-slate-200`

### Key Implementation Details

1. **ContactDrawer**: React component (`client:load`) rendered once in root layout; opened via custom `CustomEvent` from other components (avoids prop drilling). The form itself is `ContactFormBody.tsx`, which the contact page mounts too, so validation, honeypot, privacy notice and `contact_submit` exist once. Both instances are on the contact page at the same time, so each takes an `idPrefix` (`drawer`, `contact-page`) to keep field ids unique, and only the drawer passes `data-drawer-form`, which drives the staggered entrance animation in `global.css`.
2. **WhatsAppButton**: Astro component in layout, renders floating WhatsApp link. Every `wa.me` link on the site comes from `WHATSAPP_NUMBER` in `src/lib/whatsapp.ts`, which is the business number (in coexistence, on CHRod Connect's app), not the personal one. Its incoming messages get an automatic first reply from an n8n workflow outside this repo, which recognizes a quote-form message by the first line `buildWhatsAppMessage` writes (`*Nueva solicitud: …*` / `*New inquiry: …*`) and takes the client's name from the `*Nombre:*` / `*Name:*` line. If either format or the form's name label changes, the reply silently falls back to the generic greeting.
3. **Sanity SSR Config**: `astro.config.mjs` includes `noExternal` and `optimizeDeps` rules for Sanity/React dependencies—critical for SSR builds
4. **Vite Cache Issue**: `.vite` directory cleared on `predev` to prevent stale dependency resolution (Sanity + Vite can conflict)
5. **Language URLs**: both locales are prefixed (`/en`, `/es`) and their segments are translated — see `src/i18n/routes.ts`
6. **Review Form Auth**: `/review` endpoint requires `?t=REVIEW_ACCESS_TOKEN` query parameter; missing/wrong token blocks form
7. **WhatsApp Onboarding**: `/connect` (EN) / `/conectar` (ES) run the WhatsApp Cloud API Embedded Signup flow via `WhatsAppConnectButton.tsx` (FB JS SDK + `FB.login`). Two modes, chosen per client when the link is generated, never by the client: `coexistence` (number stays usable in the WhatsApp Business app — adds `featureType: "whatsapp_business_app_onboarding"` to the `FB.login` extras) and `api_only` (number, new or already in use, gets dedicated fully to the Cloud API, verified from scratch inside the popup, can no longer be used in any WhatsApp app). The card's "what you get / what you should know" copy is mode-aware and lives in `WhatsAppConnectButton.tsx` itself (not `ui.ts`), since it needs to hide once the connection succeeds. The page is gated not by a single shared token but by a per-client signature over `clientName|mode|ts|clientEmail`: `?cliente=NAME&modo=coexistence|api_only&ts=EPOCH_MS&email=CLIENT_EMAIL&sig=HMAC` (`email` is always present in the query, empty string when the admin left it blank — it's still part of what's signed, so the link can't be replayed with a swapped-in email), expiring 30 days after generation (`LINK_MAX_AGE_MS` in `src/lib/whatsappOnboard.ts`) since nothing is persisted to mark a link as already used — see that file for the signing/verification logic. Links are generated (no manual env-var editing per client) at `/es/admin-links?t=ADMIN_ACCESS_TOKEN` (admin token compared with `timingSafeStringEqual`), which calls `src/pages/api/generate-onboard-link.ts`. On completion, `src/pages/api/whatsapp-onboard.ts` re-verifies the signature (name + mode + ts + sig must match and not be expired), exchanges the `code` for a token with Meta (confirms the signup actually completed — not stored, since the client's WABA becomes accessible via our own system-user token once shared), then independently verifies `waba_id`/`phone_number_id` against the Graph API rather than trusting the client's postMessage report of them, which is both unverified and was observed arriving empty in practice. This needs **two different credential types for two different calls** — confirmed against Meta directly (each rejected the other's token with its own distinct error), not assumed: `debug_token` (on the exchanged token → `granular_scopes` → first `whatsapp_business_management` target id = the WABA) takes an **app access token** (`${appId}|${appSecret}`, query param) and explicitly rejects a system-user bearer token ("(#100) You must provide an app access token..."); `/phone_numbers` on that WABA does the opposite — it's reading real business asset data, so it needs a **system-user token** (`WHATSAPP_SYSTEM_USER_TOKEN`, same kind n8n already uses) and rejects the app access token ("(#200) You do not have permission to access this field"). Falls back to the client-reported values (no longer labeled — just shown as-is) if `exchangedToken`/`WHATSAPP_SYSTEM_USER_TOKEN` is missing or either lookup errors, and emails the result (mode + both IDs + the real display phone number when the second lookup succeeds) via Resend. That email also reports `/{waba-id}/subscribed_apps`, because a number can report as CONNECTED and still deliver nothing: message events (`messages`, `smb_message_echoes`) only flow once an app is *subscribed* to the WABA, which is separate from the app being *installed* on it — `account_update` events (PARTNER_ADDED, PARTNER_APP_INSTALLED) arrive either way, so onboarding looks healthy while the bot never receives a word. Observed on a real client number; note the subscription can also appear late, so an empty result right after onboarding is worth re-checking before treating it as a failure. Read with our own system-user token, that list only ever reports **our** app, never the full set: the portfolio that owns the WABA sees every subscribed app, while a partner with shared access sees only itself (observed 2026-10-09 on Manuarte Cartagena — our token returned one app, the client's own token returned both, with messages verifiably reaching both apps' webhooks). So an empty result means "nothing reaches us", not "nothing reaches anyone", and two apps subscribed to one WABA is a confirmed-working arrangement, not a conflict: a client running their own infrastructure gets their own app, in their own portfolio, pointing at their own API. That was a snapshot, not the current state: Manuarte's numbers are now handled only by their own app's webhook, and no Manuarte message reaches CHRod Connect's webhook (`n8n.chrod.dev/webhook/whatsapp-log`) any more. If the admin filled in a client email when generating the link (optional field in `/es/admin-links`, `clientEmail` throughout), a second, separate email also goes to the client confirming the connection (bilingual per the `lang` the client's page was in — no WABA/Phone Number ID in that one, that's internal bookkeeping, not something a client needs). No client data is persisted anywhere (deliberate MVP choice — revisit if client volume grows, e.g. Netlify Blobs). `WhatsAppConnectButton.tsx` also reloads the Facebook JS SDK when `lang` changes mid-session (View Transitions can switch between `/es/conectar` and `/en/connect` without a full reload), but this only affects the classic `FB.login` consent dialog's own chrome — verified that it does NOT control the Embedded Signup flow's language (phone entry, QR step...), which follows the Facebook account's own language setting instead, with no documented override. Not a bug to chase further, just a Meta-side constraint.

8. **Analytics**: Umami Cloud, chosen for being cookieless (so no consent banner, which a page selling fast load times cannot afford) and for allowing custom events on its free tier. Every call site goes through `track()` in `src/lib/analytics.ts` and names an event from `EVENTS`, never touching `window.umami`, so switching vendor means rewriting one function body. Nothing throws: an ad blocker or missing id leaves the global undefined and a tracking call must not take a CTA down with it. The script loads with `data-auto-pageview="false"` and `trackPageview()` fires from `astro:page-load`, which covers both first load and every View Transitions navigation. **Not `data-auto-track`**: they are different flags, and that one additionally skips patching `pushState`, which freezes the URL the payload reports on whichever page first loaded the script, so every event after a client-side navigation lands on the wrong page. That shipped once and was invisible on the home page, which is where it was tested. Each call now also passes `url` built from `window.location` at call time, so correctness no longer depends on the vendor's internal state or on a navigation having gone through `pushState`, which a back-button `popstate` does not. That url drops the hash (Umami folds it into the stored path, so the CTAs jumping to `#service-quote-form` would split a page into two rows) and keeps the search string, which carries UTM attribution. `applyTrackingToggle` runs just before each pageview: visiting any page with `?umami=off` writes Umami's own `umami.disabled` key to `localStorage` and `?umami=on` removes it, which is how the author keeps his own constant browsing out of the numbers without needing a devtools console on a phone. Per browser, per device, cleared by a site-data wipe. Seven events. `contact_open`, `whatsapp_click`, `quote_form_open` and `schedule_open` are caught by delegated listeners in `MainLayout` (on `[data-open-contact]`, `a[href*="wa.me/"]`, `a[href="#service-quote-form"]` and `[data-schedule-cta], a[href*="cal.com/"]`), so a new CTA is tracked without being wired by hand. `schedule_booked` comes from the Cal.com embed (item 9) and is the only completion metric the "Book 15 minutes" CTA has. `quote_form_open` exists because the service pages' four CTAs jump to the form rather than opening the drawer, so those pages were the only ones measuring submissions with no measure of intent, and a page nobody clicks looked like a page whose form people abandon. `contact_submit` and `quote_submit` fire from the React forms. `contact_submit` and `quote_submit{channel:email_sent}` only run on a 2xx, so they read as completion rates; `quote_submit{channel:whatsapp_opened}` can only prove WhatsApp was opened with the message composed, never that it was sent, which is why the values are named for what each proves rather than both being `email`/`whatsapp`. That path deliberately does **not** also fire `whatsapp_click`: that event measures someone reaching for WhatsApp unprompted, which is the wedge's pull, and counting form submissions in it would inflate the headline number. Note `showWhatsAppButton={false}` on service and project pages means `whatsapp_click` cannot fire there at all, so a low count on the WhatsApp service page is an artifact of there being no link, not a lack of intent. Attribution comes from `data-analytics-location` on the element, read by `readLocation` and warned about in dev when missing, because without it all 14 contact triggers report identically and the data cannot answer which CTA works. The quote form's WhatsApp button opens the link with `window.open`, so it tracks explicitly: the delegated anchor listener never sees it. `contact_submit` carries the location too, threaded from the opening CTA through the `open-contact-drawer` event's `detail`, since opens alone cannot tell a CTA that converts from one that is merely clicked. **`isAnalyticsExcluded` keeps the script off `/review`, `/resena`, `/connect`, `/conectar` and `/admin-links`**: Umami records the full URL and those carry credentials in the query string (a client's name and email plus a 30-day-valid HMAC on the onboarding links, access tokens on the others), so tracking them would file secrets and client PII in a third-party system. Same set the sitemap filter and robots.txt exclude. **Do not proxy the script through this domain.** It was tried (commit 8f8477a, reverted in the next one) to get past tracker blocklists, which Brave applies to `cloud.umami.is` by default and which make every Brave, uBlock and AdGuard visitor invisible. Two `status = 200` rules did work: the script and `gateway.umami.is/api/send` both served correctly from `/stats`, verified by md5 and by a 400 coming back from Umami itself. The cost is that Umami derives country from the IP of whoever posts the beacon, and behind a proxy that is Netlify's edge, so every visitor was recorded as Ashburn, United States. Geography is worth more here than absolute volume, because the EN side is sold on a nearshore angle and "is English pulling US traffic" is a live question, while the undercount is a roughly even bias that still allows comparing pages and reading trends. Fixing it would mean an edge function forwarding `X-Forwarded-For`, which Umami Cloud sits behind Cloudflare and very likely ignores, so it would be another silent-failure part for an uncertain gain. The numbers are therefore traffic excluding blocker users, which is a documented limitation rather than a wrong figure.

9. **Booking calendar** (`src/components/contact/ContactScheduler.astro`): Cal.com's official inline embed, one event type per language (`src/data/cal.ts`), since an event's title, description and questions are single-language. The language of each booking page is set per event in Cal.com (`es-419` / `en`), **not** "visitor's browser language": the site picks language by URL, and the browser setting would show an English calendar on `/es/contacto` to anyone with an English OS. Neither `Cal("ui")` nor the inline config accepts a locale. The embed is preferred over a plain iframe for `bookingSuccessfulV2` → `schedule_booked`, sent with no properties because the payload carries the attendee's name and a video call URL. Hard-won constraints, each one shipped broken at least once: **`theme: "dark"` must be in the `inline` config**, not only in `Cal("ui")`, or the embed follows `prefers-color-scheme` and phones in light mode get a white calendar while a dark-mode desktop looks fine. **No side padding on the card**: it narrows the booking page, which then overflows inside its own cross-origin iframe and shows both scrollbars, which no style on this side can reach (top padding is safe). The card chrome only exists from `xl` up, because below ~1024px the booking page drops its own side margins and a border makes it look pinned, and the booking page measures the iframe, which is narrower than the viewport by the `Container` gutters. While loading, the container has a fixed `height`, **not** a `min-height`: the embed creates its iframe at `height: 100%`, which cannot resolve against a minimum, so it was born at the default 150px and flashed both scrollbars before the real size arrived. The iframe stays at `opacity: 0` until the embed sets a pixel height on it (watched with a `MutationObserver`, since `__dimensionChanged` is internal), then fades in and the container goes to `height: auto`; a timeout after `linkReady` reveals it anyway in case the embed ever stops sizing it that way. Initialised from `astro:page-load` with module-scope state, since arriving from the hero CTA is a View Transitions navigation; the embed itself ignores a second `inline` call only while the previous element is still in the document, so a return visit mounts again. If `embed.js` fails to load (its `error` event, since `linkFailed` only fires once the script runs) or reports `linkFailed`, the card and the subtle header link are swapped for a fallback block with a primary button to Cal.com (`location: contact_page_fallback`); a `noscript` style does the same swap without JavaScript. After `bookingSuccessfulV2` the header link is hidden (it could only lead to a second booking) and the heading changes to one that does not repeat the confirmation Cal.com shows inside the iframe; that state is not kept, so a later visit shows the calendar again. Every reload of the page reloads the booking page, which is unavoidable: View Transitions replaces the DOM and Astro can only persist an element between two pages that both contain it. A thin scrollbar track with arrows can appear inside the booking page on Windows at narrow widths: it is Cal.com's own `overflow-y: scroll`, invisible with overlay scrollbars (macOS, iOS, Android), and not fixable from here.

10. **Blog** (`post` in Sanity, `getPosts(lang)` in `src/lib/sanity.ts`): **one document per language**, not `title`/`titleEs` like projects, because the two locales are sold on different angles and many articles exist for one market only. An optional `translation` reference pairs two documents and is set on **either** one: the query reads it from both sides, so a forgotten second field cannot leave hreflang non-reciprocal (the Studio rejects linking a post that already belongs to another pair). Slugs are unique per language, not dataset-wide. hreflang (`hasTranslation` on `MainLayout`) is emitted only between real pairs: a post and its counterpart, or the two listings when both languages have posts. The language switcher is a separate decision, made by `blogAlternates` in `src/components/blog/alternates.ts`: the counterpart, else the other language's listing if it has posts, else that language's home, so it never lands on an empty `noindex` listing. The body is Portable Text rendered to an HTML string by `src/lib/portableText.ts` (`@portabletext/to-html`) and styled by `.post-body` in `global.css`; every hand-interpolated value there is escaped, unknown block types render nothing, h2/h3 get slug ids for deep links, images get an 800/1200/1600 `srcset` from Sanity's CDN, and only web links to other domains open a new tab. Links typed in a post body are checked after every build by `src/integrations/checkPostLinks.mjs` against the real output: a dead site path is a **warning** in the deploy log, not a failure, so one typo cannot keep an article unpublished. The byline links to the about page (`rel="author"`). A post's FAQ uses `src/components/ui/FaqItem.astro`, the same card as the service pages (whole card clickable, including the open answer), so the two cannot drift apart again; only the section heading differs, since in an article it is one more h2 in the reading flow. Title length: the Studio refuses to publish a title over `BLOG_SEO_TITLE_MAX` (47) without an SEO Title, because publishing triggers the Netlify build and a title failing `assertTitleLength` would fail that build and leave the post silently unpublished. Publishing reaches the site through the Sanity webhook → Netlify build hook configured outside the repo; if that webhook filters by `_type`, `post` must be in the filter. Empty-language rules: the listing is `noindex` with no posts, `astro.config.mjs` fetches which languages have posts so the sitemap leaves an empty listing out, and the footer's "Blog" link only renders for a language with posts. The link lives in the footer, not the navbar, until there are about three articles. `getPosts` caches per language for 5 minutes (none in dev, so Studio edits show on reload): the footer asks on every page, and the per-request pages (404, review, connect) run in a long-lived function that would otherwise keep a stale answer. The site has no scheduling: a future publish date goes live immediately, which the Studio warns about.

## Common Workflows

- **Add a new project**: Edit Sanity CMS, ensure project has `titleEs` + `descriptionEs` for bilingual support. `Slug (EN)` is required and drives `/en/projects/[slug]`; `Slug (ES)` is optional and drives `/es/proyectos/[slug]`, falling back to the EN slug when empty
- **Publish a blog post**: in the Studio, create a Blog post, pick its language, fill SEO Description and Related services (the article's closing CTA points there). For an article in both languages, create two documents and set Translation on one of them. Publishing rebuilds the site; check the deploy log for `check-post-links` warnings.
- **Add a new review**: Publish in Sanity with `published: true`; form at `/en/review?t=TOKEN` (ES: `/es/resena?t=TOKEN`) submits reviews to Sanity
- **Onboard a WhatsApp client**: go to `/es/admin-links?t=ADMIN_ACCESS_TOKEN`, enter the client's name, copy the generated link, send it to them. No deploy or env var edit needed per client.
- **Update text/copy**: Edit `src/i18n/ui.ts` for static UI strings; Sanity for dynamic content (projects, reviews)
- **Add a React component**: Use `client:load` directive to hydrate; Astro handles SSR
- **Deploy**: Push to main branch; Netlify auto-deploys (see `netlify.toml` if exists, or Netlify UI config)
